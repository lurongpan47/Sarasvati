## What I did
1. Upgraded the rolling stamp via temp copy; verified the Bitcoin attestation with py-opentimestamps (deserialised the proof, walked the tree to the `BitcoinBlockHeaderAttestation`); resolved block hash + timestamp on mempool.space.
2. Upgraded the 09-17 `.bak` stamp the same way (kept, gitignored).
3. Trashed the redundant `SHA256SUMS.ots.bak` (its content is a strict subset of `SHA256SUMS.pre-2026-09-17.ots.bak`, which is already upgraded to 966985). `trash`, not `rm`.
4. Patched `scripts/ots_upgrade_watch.sh` to upgrade a temp copy and move it back only when attestations were gained. Syntax-checked and dry-ran it.
5. CHANGELOG entry with heights, hashes, mined-at times, calendar, and a note that this verification-day commit is not re-hashed (same convention as 09-16).

## Which principle applied
- **Satya** — the archive's claim is "provably dated", not "we say so". Heights come from the deserialised proof, block hashes from an independent explorer; I did not write "confirmed" from the `Success!` line alone (the first run said "Success" and had changed nothing).
- **Sati** — the `.bak` no-op is exactly the kind of quiet failure that makes an integrity layer decorative. Named, fixed, logged.
- **Anattā / satya on the erratum** — keeping the superseded 09-17 stamp (the one that anchors the *wrong* file) rather than discarding it. An erratum that erases the evidence of the error isn't one.
- **Sampajañña** — `ots verify` still fails without a local Bitcoin node; the presence of the `BitcoinBlockHeaderAttestation` in the proof is the confirmation, and anyone with a node can verify independently.

## What I rejected
- **Re-hashing the manifest today** to include this CHANGELOG/decision file. Rejected — would replace a confirmed stamp with a pending one every single day and the corpus would never be "currently anchored". Content pushes re-stamp; verification pushes record.
- **Deleting the old 09-17 stamp** as "wrong". Rejected, see above.
- **Also starting the retroactive spot-check audit.** Rejected — one thing per push, and that task deserves the scans open and undivided attention.
- **Scheduling `ots_upgrade_watch.sh` in crontab.** Not done — it's not asked for, and the daily push already covers it; adding a scheduler entry without Pan seeing it isn't worth the small convenience.

## What would have blocked me
- If the temp-copy upgrade had still shown only pending attestations → CHANGELOG would say "still pending as of 2026-09-19", nothing more.
- If mempool.space had disagreed with the proof's height → I would have recorded the discrepancy, not picked one.
